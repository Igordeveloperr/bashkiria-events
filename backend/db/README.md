## Исходные страницы парсера

Ревизия `0002_parser_raw_documents` добавляет таблицу `parser_raw_documents`:
UUID `id`, `source_id`, `url`, `fetched_at` (`timestamptz`, UTC), `http_status`,
исходный текст `content` и SHA-256 `content_hash`. Хеш считается по UTF-8
представлению декодированного текста ответа.

Каждая загрузка сохраняется отдельной строкой, даже если содержимое не изменилось.
Ответы 4xx/5xx также сохраняются; сетевые сбои без полученного ответа строки не создают.
Таблица не содержит нормализованные события и не публикует их. Откат этой ревизии
удаляет только исходные документы парсера, не затрагивая таблицы чатов.

Настройки подключения и запуск парсера описаны в [Parser README](../parser/README.md).

## Нормализованные данные и задания парсера

Ревизия `0003_parser_pipeline` создаёт:

| Таблица | Назначение |
| --- | --- |
| `parser_events` | Нормализованные события, статусы публикации и источника, уверенность, причины проверки, версия записи |
| `parser_event_sources` | Связь события с источниками и последними сырыми документами, устойчивый ключ записи источника |
| `parser_event_audit` | Журнал сбора, изменений и модерации |
| `parser_collection_runs` | Очередь фонового сбора, отчёт, аренда задания исполнителем и восстановление после прерывания |

Модели и Fluent API сопоставления находятся в `backend/parser/parser/Models` и
`Data/Configurations`. Парсер обращается к PostgreSQL через EF Core 10 и только
асинхронными ORM-операциями. EF Core не создаёт схему и не применяет миграции:
единственный механизм изменения схемы — этот сервис Alembic.

Уникальные индексы защищают дедупликацию событий, идентичность записей источников
и единственный активный запуск на источник. Связи с исходниками используют
`RESTRICT`: удалять документы, на которые опираются события, нельзя.

Откат ревизии удаляет таблицы событий и заданий парсера с их содержимым,
сохраняет сырые документы и не затрагивает историю чатов.

## История диалогов

Схема чата создаётся ревизией Alembic [0001_chat_history](migrations/versions/0001_chat_history.py).
Эта ревизия создаёт только чат; исходники и таблицы парсера добавлены ревизиями 0002 и 0003.

| Таблица | Назначение | Основные поля |
| --- | --- | --- |
| `chat_sessions` | Диалог конкретного пользователя | UUID `id`, строковые `user_id` и `session_key`, `title`, `next_seq`, время создания и обновления |
| `chat_runs` | Один запрос генерации | UUID `id`, `session_id`, UUID `request_id`, статус `running/completed/failed`, `trace_id`, ошибка и время завершения |
| `chat_messages` | Полная история | UUID `id`, `session_id`, `run_id`, порядок `seq`, роль `user/assistant`, текст, дополнительные данные `jsonb`, время создания |
| `alembic_version` | Текущая ревизия схемы | `version_num` |

Все даты чата имеют тип `timestamptz`. Владелец задаётся внешним строковым `user_id`;
таблица пользователей не дублируется. Ключ диалога уникален внутри пользователя.
Порядок сообщений задаётся `seq`, уникальным внутри диалога. Ограничения БД
запрещают повторный `request_id` в диалоге, два активных запуска и несколько
сообщений одной роли в одном запуске. В текущем графе один запуск содержит вопрос
и один ответ; сообщения инструментов потребуют отдельной миграции при добавлении поиска.

Полная история хранится независимо от скользящего окна модели. В контекст попадают
только последние завершённые пары. Запросы истории фильтруются по владельцу,
а повторные сообщения распознаются по `(session_id, request_id)`.

## Запуск через корневой Compose

Все сервисы описаны в корневом `compose.yaml`. Запуск из корня репозитория:

```powershell
docker compose up -d --build
docker compose wait migrate
docker compose logs migrate
```

Строка подключения по умолчанию:
`postgresql://bashkiria:bashkiria@localhost:5432/bashkiria`.
Другой порт можно задать через `POSTGRES_PORT`. Данные сохраняются в Docker volume.

Сервис `migrate` ждёт PostgreSQL с успешным healthcheck, выполняет
`alembic upgrade head` и завершается. Код 0 означает успешный запуск, включая
ситуацию без новых ревизий. Ошибка возвращает ненулевой код. Для будущего HTTP
backend укажи `depends_on: migrate: condition: service_completed_successfully`
вместе с зависимостью от здорового PostgreSQL.

Внутри Docker используются `PGHOST=postgres`, `PGPORT=5432` и остальные переменные
PostgreSQL. Пароли передаются отдельными значениями, поэтому специальные символы
не требуют URL-кодирования. Настройки берутся из корневого `.env` или значений
по умолчанию Compose. Для подключения CLI с компьютера используется `DATABASE_URL`
в `backend/ai/.env`, с адресом `localhost` и опубликованным портом.

Повторно применить миграции и посмотреть текущую ревизию:

```powershell
docker compose run --rm migrate
docker compose run --rm migrate alembic current
docker compose run --rm migrate alembic history
```

Образ миграций собирается только из `backend/db`, устанавливает зависимости по
собственному `uv.lock` и не включает AI-сервис, его `.env`, ключи и сертификаты.

## Создание новых ревизий

Из `backend/db`:

```powershell
uv sync --frozen
uv run --frozen alembic revision -m "add event tables"
uv run --frozen alembic upgrade head
uv run --frozen alembic current
```

В новой ревизии заполни `upgrade()` и `downgrade()` через `alembic.op`/SQLAlchemy.
Ревизии пишутся явно. EF Core модели парсера не являются SQLAlchemy metadata;
`--autogenerate` потребует отдельной актуальной SQLAlchemy metadata.
Применённые ревизии не редактируются. После добавления файлов пересобери сервис
командой `docker compose up -d --build` из корня.

Локальный Alembic читает `DATABASE_URL` из окружения, затем корневого `.env`
или `backend/ai/.env`. Также поддерживаются `PGHOST`, `PGPORT`, `PGUSER`,
`PGPASSWORD`, `PGDATABASE`. Для миграций ключи GigaChat и Langfuse не нужны.

Откат предыдущей ревизии выполняется явно: `alembic downgrade -1`. Начальная
ревизия при откате удаляет таблицы чата вместе с их данными; при обычном старте
Compose выполняется только `upgrade head`.

## Переход со старой SQL-миграции

Имя Compose-проекта и Docker volume сохранены при переносе Compose в корень.
Начальная ревизия распознаёт `ai_schema_migrations` от прежнего `migrate.py`,
проверяет контрольную сумму [старого SQL](legacy/001_chat_history.sql) и структуру
существующих таблиц, после чего записывает версию Alembic без пересоздания таблиц.
Переписка, UUID и счётчики `seq` сохраняются. Старая служебная таблица остаётся
как запись о происхождении схемы; новые версии учитывает `alembic_version`.

Если обнаружены неизвестная контрольная сумма, неполная схема или таблицы чата
без старой записи миграции, процесс завершается ошибкой и не штампует такую БД.
Самописный runner удалён; файл в `legacy` нужен только для проверки совместимости.

## Проверки

Из `backend/db`:

```powershell
uv run --frozen python -m unittest discover -s tests -v
```

Для интеграционных тестов задай `TEST_DATABASE_URL` тестовой PostgreSQL в окружении.
Каждый тест создаёт собственную случайную схему и удаляет только её. Проверяются
создание, повторный запуск, откат, конкурентный запуск двух процессов миграций,
сохранность старой переписки и отказ от принятия неизвестной/изменённой схемы.
Без этой переменной выполняется только проверка генерации SQL без подключения к БД.

Подробности AI-сервиса — в [AI README](../ai/README.md).
